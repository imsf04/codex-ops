# 0.8.0最终验收结果

**0.8已有收益，但没有达到既定发布门槛。当前仍启用0.7，未安装0.8；桌面使用的原沙箱环境已恢复。**

完整新鲜对照共132次，以下成本只比较双方都成功的配对任务：

| 指标 | 对0.6.1（31对） | 对0.7（43对） |
|---|---:|---:|
| 原生动作减少 | 16.19% | 7.75% |
| 外层调用减少 | 6.80% | 10.63% |
| 输入token减少 | 7.44% | 13.65% |
| 未缓存输入减少 | 7.79% | 12.60% |
| MCP进程启动减少 | **增加66.67%** | 65.22% |

对0.6.1要求动作减少25%、输入减少20%，都未达到。严格通过数：0.6.1为33/36，0.7为45/48，0.8为43/48，因此质量不回退门槛也未通过。每组各3次失败来自终端包装器退出码问题；独立修正包装器的补充试验9/9通过，原132次记录不替换、不重新计分。0.8还多出两次日志答案字段错误：要求整数行号5001，模型填写了日志正文；交付视图实际包含5001，失败仍保留。

工作流确实更常用了：0.8显式采用26/48（54.17%），0.7为22/48（45.83%）；加上实际观测到的自动交付，0.8覆盖29/48（60.42%）。仅保存事件不计入服务，旧版没有自动交付插桩，不能视为零。**这是受控基准，不是日常使用率；日常采用率目前未知。**

未达到目标的原因已经落到具体轨迹：中文问题缺乏有效自动锚点后还要再次找文件；工具发现有时单独占一轮；小任务原本只有两次调用，输出很少；原生命令的合并方式有模型波动。每多一轮约重新输入1.6万token，几百字的压缩抵消不了。新工作流自动锚点仅覆盖英文是当前能力缺口；三版本共有的诊断来源路径解析错误是另一个继承问题，不能混为新回归，也不能据此解释所有答案字段失败。

确定性验证通过：543项Python测试，96个模块932个函数CRAP均≤6，覆盖率98.99%；Rust40个函数最大CRAP5.0043。原生协议、轮询、失败退出状态、修订后新内容、完整原值恢复亦有对应验收。质量指标通过不代表模型成本门槛通过。

可审阅的后续选择：

- **继续优化再安装：** 优先消除单独发现工具的轮次、补齐中文/无匹配后的有界检索、修复诊断契约并重新跑固定对照。当前0.7继续使用。
- **明确接受门槛未达后实验启用：** 接受上述成本缺口及严格失败，保留0.7完整回退，单独记录例外与重启验收。现在没有执行此选择，旧版曾获例外不自动延续。
