# 0.8 实际采用与成本调查

日期：2026-10-30。英文及完整证据索引：[analysis-0.8-usage.md](analysis-0.8-usage.md)。本次只分析既有记录，没有新增付费模型实验或修改生产实现。

## 采用率现在能说到哪里

重启请求记录于 02:17:23.301 UTC，本轮研究始于 02:21:39.697 UTC。扫描本机 39 份十月 rollout 后，重启验收阶段有 investigate 5 次、verify 2 次；本轮插件研究另有 investigate 1 次。尚无独立标注的日常任务机会样本，**不能据此计算日常采用率，也不能写成 0%**。

5 次验收 investigation 中，2 次参数错误、1 次无匹配、2 次采集到证据。7 次 MCP 的宿主状态全部是 completed，说明“调用正常结束”不能替代“拿到有用证据”。终生计数还混合旧版本、开发、验收。详见[按时间与用途分组的记录](../verification/v080-live-rollout-audit.json)。

冻结模型实验每版 36 次尝试：至少使用一种 workflow 的尝试从 23/36（63.9%）变为 21/36（58.3%）。0.7 的 investigate 被选择 21 次，documents 4 次，diagnose 3 次；evidence、working_set、verify 均没有被自然选择。这是**包含工作流的尝试占比**，不是适用机会采用率；实验提前注入 skill 和模拟 SessionStart，也不等同日常按需加载。新 investigate 替换了 locate/incremental，但整体覆盖面没有扩大。[冻结汇总](../verification/v070-cost-summary.json)

## 未达标的缺口与优先修复处

28 组共同成功任务：原生动作 197→159，下降 19.29%；输入 token（含缓存）5,999,077→5,036,759，下降 16.04%；非缓存输入下降 7.07%。按原定 25%/20% 目标，同一组任务还差至少 **12 个原生动作、237,498 个输入 token**。

| 共同成功任务 | 配对数 | 原生动作 0.6.1→0.7 | 输入 token 0.6.1→0.7 |
| --- | ---: | ---: | ---: |
| 冲突文档判断 | 3 | 13→20 | 400,879→675,434 |
| 代码定位并找到回归测试 | 3 | 14→12 | 420,981→555,408 |
| 中文业务术语 | 3 | 31→19 | 959,529→553,817 |
| 恢复部分工作 | 3 | 32→21 | 979,667→660,162 |
| 修复测试/配置 | 3 | 37→29 | 956,945→822,528 |

两个输入退步的任务组比基线多 408,982 token。若冲突文档组恢复到基线，算术上总输入降幅达到 20.62%；两个组都恢复则为 22.86%。其中也有 Windows 宿主工作目录失败，**这不是插件可保证实现的收益**。[完整分组数据](../verification/v080-benchmark-task-deltas.json)

实际调用链揭示了可操作的问题：

- 冲突文档第一次：先两次原生列文件失败；documents 把 DOCX 交给普通 read，随后又取 raw、再用原生命令解析 ZIP/XML。应让入口识别格式并选择 read_docx。
- 冲突文档第三次：investigate 只找到草稿 Markdown/CSV，漏了正式 DOCX；glob 的 string/array 参数又试错一次，随后多次 glob/read。应一次交付来源、正式/草稿身份以及冲突证据。
- 代码定位第二次：问题明确要求实现和回归测试，首次 investigate 只交付实现及周边文件；原生查测试目录失败后，第二次 investigate 才找到测试。应按问题的多项证据需求安排检索和预算。
- 恢复部分工作有一次确认由展示造成的回读：摘要隐藏成功文档与 ACCESS_DENIED。错误、部分成功状态和缺失证据应优先展示。

原始回读次数是 1→3；候选有 1 次确认由展示导致，其余因果未知，不能说回读目标已达成。外层调用数只有 30/36 组具备原始观测，其中共同成功子集 23 组，不应混同全部 28 组。[工具审计](../verification/v070-combined-tool-audit-final.json)、[失败审计](../verification/v070-final-failure-audit.json)

## Rust 是否是当前主要解法

共同成功候选任务的 wall time 合计 1,704.737 秒；原生事件记录的 27 次 workflow 合计 15.047 秒，中位 563 毫秒；全部插件工具合计 20.325 秒，约为任务 wall time 合计的 1.19%。全部已记录原生工具耗时 153.797 秒，约 9.02%。基线 workflow 中位 415 毫秒。

这些是宿主记录的工具耗时，**不是 CPU profile，也不是重写收益上限证明**：有并行、缺失耗时，且包含启动与传输开销。但现有证据更支持先减少模型往返、错误路由和无用证据，再按实测瓶颈把特定路径迁入 Rust。原始 worker 已是 Rust。[逐调用计时记录](../verification/v080-observed-tool-duration.json)

## 建议顺序

1. 类型化的文档/代码/日志入口，正确的最短参数，覆盖问题明确要求的测试或权威来源。
2. 可直接消费的证据输出，保证错误与部分成功状态；避免 raw 的完整结果又被外层压缩成另一个引用。
3. 用任务形态暴露高价值工作流，精确小读取仍用原生；衡量有用证据和避免的后续读取，而非鼓励刷调用量。
4. 分开统计日常任务、验收、开发和模型实验；先明确每种工作流的适用机会，再计算采用率。
5. 修复具体退步用例后再跑冻结成本实验，成功率、缓存/非缓存输入、输出、外层调用、原生动作及延迟分别记录。
6. 对启动、worker 进程、序列化和 CPU 热点做 profile；有证据再用 Rust 替换，同时保持权限、失败、轮询和原值恢复契约。
