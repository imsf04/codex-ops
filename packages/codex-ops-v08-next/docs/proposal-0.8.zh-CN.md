# Codex Ops 0.8 决策建议

日期：2026-10-30。状态：调研与提案；未修改生产实现、未重装、未启动新的付费模型试验。0.7.0 保持运行。

## 决策

建议以“更少往返、更完整的一次交付”为 0.8 的主目标，同时推进有证据支持的 Rust 内核整合。暂不做整套 Python 到 Rust 的等价重写。文件搜索/文档底层已经是 dsh-ops Rust worker；语言迁移不会自动改善工具选择、证据遗漏、宿主权限或模型 token。

## 当前证据

- 上游主线核对到 02b1c0c147025ae30df977227cdbfd68c6f77a2e；独立包版本仍为 0.5.0。Codex Ops 0.7.0 不是上游 0.7。最近相对本地基线的 19 个提交没有改变 native Rust 目录。比较与固定来源见 [上游调研](research-0.8-upstream-rust.md)。
- 重启后的首批新工作流调用是明确的验收：5 次 investigate、2 次 verify；其中调查有 2 次请求错误、1 次无匹配、2 次取得证据。随后是本轮调研使用。没有足够独立日常任务，不能报告日常采用率百分比。
- 冻结模型试验中，使用任意工作流的任务为 23/36 → 21/36；investigate 出现在 21/36 个候选任务。evidence、working_set、verify 没有自然选择证据。58.3% 是试验任务覆盖比例，不是有资格机会中的采用率。
- 28 个共同成功任务：原生动作 197 → 159（减少 19.29%，目标 25%）；输入 token 5,999,077 → 5,036,759（减少 16.04%，目标 20%）；未缓存输入 639,205 → 594,007。总体严格成功 29/36 → 34/36。冻结结果仍为 FAIL/UNKNOWN，用户接受启用的决定独立保存。
- 原生动作不包括 MCP 内部 worker 启动，外层 exec 也单独计量。不能把任何一个指标改称全系统总调用。
- 冲突文档核对多 7 次动作、274,555 输入 token；代码定位少 2 次动作却多 134,427 输入 token。前者存在 DOCX 当文本读、补取、手动 ZIP 解析；后者存在相关测试未入首包、随后再查。见 [冻结模型报告](../verification/v070-costs-combined.json) 与 [失败审计](../verification/v070-final-failure-audit.json)。
- 达成旧门槛，当前共同成功样本尚需少 12 次动作、237,498 输入 token。若仅把冲突文档输入恢复至基线，算术上已超过 20% 降幅；这只是定位优先级的反事实计算，不是对下一版收益的保证。

## 本轮直接测量

完整能力比较不能仅按 MCP 工具名计数：0.7 已有精确编辑/写入计划、CAS、恢复回滚、诊断和 HTML 看板；命令与变更执行刻意交给 Codex 原生权限链。尚未对齐的是 DSH 的动态工具发布/替换、内置 PTC 注册协议、嵌入宿主的侧栏等。机器数据/模型呈现的双投影仍值得深化。详见[完整能力分类](research-0.8-upstream-rust.md)。

[局部计时](../verification/v08-local-profile.json) 使用当前生产 Python、独立临时存储、串行 7 次。含首个样本，不含模型/MCP传输/冷启动。不是端到端基准。

| 项目 | 中位数 | 观察 |
| --- | ---: | --- |
| 读取 44 行 | 26.0 ms | 已调用 Rust worker |
| 单文件单锚点 investigate | 112.1 ms | grep/read/grep/read，4 次 worker 启动 |
| 约 61 KB 日志呈现 | 6.23 ms | Python 呈现与保存路径 |

[证据包样本](../verification/v08-packet-profile.json)：11 行源码文本合计 688 字符，整个包 7,986 JSON 字符，MCP 信封 13,591 字符。字段包含必要的来源、覆盖与继续入口，但路径/修订和多阶段说明重复。字符数不是 token；单一样本也不代表所有包。

当前 `focus` 在 [investigate_query.py](../investigate_query.py) 校验，在 [evidence_packet.py](../evidence_packet.py) 回显；[investigate.py](../investigate.py) 的检索/扩展没有按 focus 改变策略。当前是有界字面调查，不是定义/引用/配置/失败的完整差异化计划。

## 六项优先工作

1. **一次交付可判断的证据。** 机器完整 data 与模型精简 view 分开；来源表按文件去重，保留行号；错误、退出码、冲突、缺失来源优先。局部文档成功与失败必须同时可见。多结果帧按信息重要性分配预算，避免小而关键的状态被大结果挤掉。原始值与逐页精确恢复契约不变。
2. **按意图选择调查材料。** definition/references/configuration/failure 真正改变检索与扩展；代码问题包含适用的调用处、测试和配置，文档核对自动识别 DOCX/PDF/表格并提示来源冲突。不要靠增大所有预算解决。稳定排序、排除构建/验证产物、明确未覆盖范围。
3. **常用入口无需额外准备。** 保持 root + question 的简洁默认；将关键参数约束放入模型实际可见契约，避免 generic args 隐藏限制。比较专用工具与单入口判别式 schema 的完整成本后再决定。根据文件类型自动分派，返回可直接使用的下一步，SDK 继续可选。不得以绕开原生权限换取“自动化”。
4. **工作集成为自然的增量路径。** 在可证实的同 chat/root 范围记录已取得的证据、未解决问题和文件修订；下一轮复用有效证据，仅刷新变化部分。证据已有时直接查已有引用。不能把自动输出的 Code Mode 标识猜作 chat ID，也不能恢复过期授权或声称删掉宿主历史上下文。
5. **验证结果自动提供诊断。** 对已经观察到的原生命令失败/轮询完成生成紧凑结果与诊断；避免再调用一次 verify 才知道错在哪里。原生命令、审批、取消和写入仍走宿主；不新建绕开审批的 MCP 命令执行器。长任务只在有进展/完成/失败时给有效输出，原始 chunks 和终态完整保留。
6. **Rust 内核整合与可信成本归因。** 首先复用现有 Rust crate，新增有边界的“搜索 + 上下文”复合请求，尝试将当前单文件调查 4 次 worker 启动降到 1 次。现有 ops-batch 是 copy/move/remove 事务，不能冒充只读调查批处理。存储/索引/呈现是否迁移，以测量及维护收益决定。先不常驻化：worker 的 EOF 请求和 process-exit 超时必须先处理取消/生命周期。成本计量按版本、chat、任务、生产/验收分 cohort，分别统计外层调用、原生动作、worker 启动、缓存/未缓存 token、补取、错误和端到端时间。

## 验收顺序

- 先修复两个已经出现回归的任务族，保留旧失败、旧阈值和 0.7 回退；增加未用于调参的代码/测试、冲突文档、错误轮询留出任务。
- 在真实按需工具发现条件下验证，不只提前注入完整 skill；任务不点名强制工作流。事先标注 eligible opportunities，以首选、有效证据、是否继续补查来衡量采用。
- 成本以共同成功任务为主，同时报告全部尝试和失败；若任何迁移降低成功率，不把 token 更少视为胜利。原有 25%/20% 是相对 0.6.1 的门槛，另报告 0.8 对 0.7 的增量，不能混分母。
- 建议在旧门槛之外设置探索目标：相对 0.6.1 动作减少 35%、输入减少 30%，同时不增加未缓存输入和失败。它们是提议的 stretch targets，不是已达成或用户已批准的门槛。
- Rust 单独建立覆盖率与圈复杂度对应关系并实际计算 CRAP ≤6；当前 Python 的 797 函数记录不覆盖 Rust。先做差分协议、取消、错误、分页和原始值一致性检查，之后才比较速度。
- 可先交付证据/路由/调查改进，再晋级已证明有收益的 Rust 复合内核；不让全量语言迁移阻挡用户能感受到的减少往返。
